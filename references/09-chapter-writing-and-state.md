# 章节写作与长篇状态

本参考用于原创项目中的写章、续写、修订与状态回写。项目专属 writer Skill 应把这里的规则落实到每一章。

## 一、项目定位与加载顺序

从当前目录向上查找 `NOVEL_PROJECT.md`；找不到时使用用户给出的项目路径。加载顺序固定为：

1. `NOVEL_PROJECT.md`：确认项目、当前阶段和锁定 pack；
2. `style/PACK_MANIFEST.md`：确认 ID、版本和状态；
3. `style/WRITING_STYLE_CONTRACT.md`：加载 always-on 规则和场景模式；
4. 本章 `outline/chapters/<chapter-id>.md` 或总纲中的本章条目；
5. `state/CURRENT_STATE.md`；
6. `bible/STORY_BIBLE.md` 中与本章实体相关的部分；
7. `state/PLOT_THREADS.md` 中到期、相关或高优先级线程；
8. `state/TIMELINE.md` 中与本章时间地点相关的事件；
9. 上一章记录、摘要和必要尾段。

风格契约必须先于正文构思进入上下文。不得加载来源审计目录来“加强风格”。

长篇较大时按需读取 Bible 和时间线的相关部分，但始终完整读取当前状态、当前蓝图和风格契约。上下文不足时优先保留硬规则、人物知识、上一章结果和本章任务，压缩远期大纲的说明性文字。

## 二、PREPARE：准备上下文

准备一份临时 chapter context，不把它写成 canon。至少回答：

- 这一章开始时，时间、地点、在场人物与 POV 是什么？
- 每个在场人物知道什么、不知道什么、误以为什么？
- 上一章造成了哪些不可撤销结果？
- 哪些承诺、线程或伏笔已经到期？
- 本章必须推进什么，不能提前揭示什么？
- 风格契约的 always-on 常量是什么？本章需要哪些场景模式？

发现状态互相矛盾时暂停起草，列出冲突文件与最小修复建议。不要在正文中悄悄选择一个版本。

## 三、PLAN：章节蓝图

使用 `templates/CHAPTER_BLUEPRINT.md.template` 创建或补全蓝图。每章必须有一个可观察的状态变化，而不只是气氛或信息堆叠。

蓝图至少包含：

- 章节目标、人物即时目标、阻力与代价；
- 开始状态与结束状态之间的变化；
- 场景卡：地点、POV、目标、阻碍、转折、信息释放、情绪回报、退出钩子；
- 必须触及与禁止触及的线程；
- 每个场景的 style mode 与强度；
- 连续性风险和验收标准。

如果用户只说“下一章”，从总纲、当前压力和到期线程推导蓝图。若推导结果会改变主线方向，先展示简短方案；局部执行选择可直接作出。

## 四、DRAFT：按契约起草

### 稳定层与场景层

- 稳定层始终生效：POV、时态、叙述权限、叙述距离范围、声音温度和硬禁忌。
- 场景层随任务变化：句长、段落密度、对白比例、感官通道、解释量、内省深度、信息释放速度和意象强度。

“每章都使用蒸馏风格”是指每章都受同一契约约束，不是每段都重复同一组表面特征。动作场景可以压缩句长，内省场景可以扩大停留时间，只要仍在契约边界内。

### 起草优先级

发生冲突时按以下顺序处理：

1. 用户对本章的明确要求；
2. 已验收 canon 与硬世界规则；
3. 人物知识边界、POV 和时间线；
4. 本章目标和大纲承诺；
5. 锁定风格契约；
6. 局部修辞偏好。

风格不能成为破坏事实或人物逻辑的理由。

### 来源隔离

起草时不得：

- 搜索或读取来源小说正文、审计证据和来源画像；
- 复用来源专名、独特比喻、标志性句式或连续情节节拍；
- 用作者名或书名补充契约中没有的风格规则；
- 把原创角色映射为来源角色的一一对应物。

## 五、REVIEW：五道检查门

完成草稿后逐门检查并修复：

### 1. 任务门

- 本章目标是否实现？
- 章首到章尾是否有明确变化？
- 结尾是否产生与类型承诺相符的推进力？

### 2. 连续性门

- 时间、地点、物件、伤势、资源和关系是否连续？
- 人物是否只使用自己已知的信息？
- 是否错误兑现、遗忘或重复某个线程？

### 3. 叙事门

- POV、时态、叙述距离和信息权限是否合规？
- 是否无标记跳头、提前解释或泄露作者真相？

### 4. 风格门

- always-on 常量是否全程稳定？
- 场景模式是否与场景功能匹配？
- 是否出现固定句式、意象、段落节拍或结尾手法的机械重复？
- 是否为追求表面“像”而牺牲清晰度、角色或推进？

### 5. 原创与来源泄漏门

- 是否出现来源身份、专名、独特表达或可识别世界设定？
- 是否连续复刻多个辨识度高的来源情节节拍？
- 是否可以仅用中性机制解释当前写法？

任何硬失败都必须修复后再交付。

## 六、DELIVER：交付但不提交 canon

交付内容通常包括：

1. 章节标题与完整草稿；
2. 极简说明：使用的主要场景模式、已推进线程和仍需用户决定的问题；
3. 明确当前状态是 `DRAFT / NOT COMMITTED`，等待接受或修订。

不要把详细内部推理、来源证据或逐条自评分塞进正文。用户只需要能阅读和判断的章节。

如果任务是在仓库中直接写文件，可以将草稿保存为明确带 `draft` 状态的文件，但不得更新 `CURRENT_STATE.md`、`TIMELINE.md` 或线程状态。

## 七、ACCEPT / COMMIT：原子化回写

这里的 `COMMIT` 是 canon 状态提交，不是 Git 操作。除非用户另外要求，不执行版本控制提交或推送。

以下任一情况视为接受：

- 用户明确说接受、定稿、提交或采用；
- 用户在收到该草稿后直接要求写下一章，且没有提出修订。

提交顺序：

1. 把章节正文保存到稳定路径并标记 `ACCEPTED`；
2. 使用 `templates/CHAPTER_RECORD.md.template` 写章节记录；
3. 更新 `TIMELINE.md` 中本章实际发生的事件；
4. 更新 `PLOT_THREADS.md` 中新建、推进、兑现、延后或废弃的线程；
5. 更新 `CURRENT_STATE.md` 为下一章开场所需的紧凑状态；
6. 更新大纲章节状态；只有用户同意的范围变化才改主线计划；
7. 最后更新 `NOVEL_PROJECT.md` 的当前章节和阶段。

每次更新只记录本章引起的变化，保留稳定 ID 和来源章节。不要重写历史来掩盖矛盾。

提交后复核：章节记录、当前状态、时间线和线程账本对同一事实的表述必须一致。

## 八、修订与回滚影响

### 未验收草稿

直接修订草稿和蓝图，不推进当前章节，也不更新 canon。

### 已验收章节

先进行影响分析：

- 哪些后续章节依赖被改事实？
- 哪些人物知识、关系、物件状态、时间线事件和线程会变化？
- 这是局部措辞调整，还是 canon 变更？

纯措辞调整在重新通过风格和连续性检查后替换正文，并在章节记录留下修订说明。Canon 变更必须先向用户列出影响范围；获得确认后按章节顺序重算相关记录和当前状态。

不要删除旧事实的痕迹。用 `superseded`、修订号或变更记录说明替代关系。

## 九、上下文压缩规则

`CURRENT_STATE.md` 应保持高信号而不是无限增长：

- 只保留写下一章仍然有效的状态；
- 已结束细节移入相应章节记录和时间线；
- 长期稳定设定放入 Bible，不在每章重复；
- 线程细节放入 `PLOT_THREADS.md`，当前状态只列近期压力；
- 上一章保留摘要和必要尾段指针，不复制整章。

压缩不能丢失硬事实、人物知识边界、未兑现承诺、资源变化和不可逆后果。
